# kwx_ts

`kwx_ts` is a standalone, self-contained TypeScript runner for the kwxFFI
wxWidgets bindings. It embeds QuickJS-ng (JavaScript engine), Sucrase
(TypeScript transpiler), and a statically linked kwxFFI/wxWidgets, so a single
executable can run a `.ts` entry file that drives a native wxWidgets GUI.

There is no dependency on a system Deno, Node, or npm install at runtime. The
only dynamic libraries the executable loads are those provided by the operating
system.

## Usage

```
kwx_ts <entry.ts> [args...]
```

- `entry.ts` — the entry module. Relative and absolute filesystem paths are
  supported (see [Module resolution](#module-resolution)).
- `args...` — passed through to the program as `args` from `kwx/platform`.

Example (Windows, Release build, run from the repository root):

```
bin\Release\kwx_ts.exe kwx_ts\examples\hello.ts
```

Example (macOS / Linux, Release build):

```
bin/Release/kwx_ts kwx_ts/examples/hello.ts
```

Use the Release binary when startup time matters: a Debug build is roughly 1.6x
slower from process start to a visible window.

### Output streams and exit codes

- Program output (`console.log`, `console.info`, `console.debug`) goes to
  **stdout**.
- Diagnostics (`console.warn`, `console.error`, and loader/transpiler errors)
  go to **stderr**.
- Exit code `0` on success. A non-zero exit code is produced by `exit(n)` from
  `kwx/platform`, by an uncaught error, or by a usage error (missing entry file
  → `2`).

### Startup tracing

Set `KWX_TS_TRACE` to any non-empty value to have the host print one timestamped
line per initialization phase to **stderr**. With the variable unset nothing is
printed and stdout is unaffected.

```
set KWX_TS_TRACE=1
bin\Release\kwx_ts.exe kwx_ts\examples\hello.ts
```

```
[kwx-trace]     14.70 ms  pre-main
[kwx-trace]      0.00 ms  main-begin
[kwx-trace]      0.06 ms  runtime-created
[kwx-trace]      0.30 ms  context-created
[kwx-trace]      0.34 ms  native-object-created
[kwx-trace]      0.41 ms  bindings-registered
[kwx-trace]      0.83 ms  host-runtime-evaluated
[kwx-trace]      0.87 ms  run-main-begin
```

The leading `pre-main` line measures process creation to entry into `main()`
(Windows only; on other platforms it is omitted). Its value is independent of
the `main-begin` origin — it is the elapsed time since the OS created the
process, so it can exceed the other timings.

Native phases: `pre-main` (Windows), `main-begin`, `runtime-created`,
`context-created`, `native-object-created`, `bindings-registered`,
`host-runtime-evaluated`, `run-main-begin`, `run-main-end`. Loader phases, per
module: `entry-resolved`, `module-read`, `transpile-cache-hit` /
`transpile-cache-miss`, `transpile-begin` / `transpile-end`,
`module-compiled`, `module-factory-built` (the `new Function` compile) and
`module-executed`, plus `symbols-resolved:<count>` (FFI thunks created on
demand so far). JavaScript can add its own mark with
`kwxHost.__kwx_trace(label)`.

Sucrase is no longer loaded during `kwx_runtime_init()`. It loads lazily on the
**first transpile**, so a plain `.js` entry that never needs transpiling never
pays the bundle cost; `sucrase-bundle-evaluated` is emitted at that point
instead of during initialization.

FFI thunks are registered lazily. Initialization installs only a name → thunk
resolver: a thunk is created the first time the corpus (or a script) reads
`dlopen(...).symbols.<name>` or `kwxHost.<name>`. Both surfaces are proxies
over one cache, so a run pays only for the symbols it touches; the
`symbols-resolved:<count>` mark reports how many were created by the end of
startup. Numeric constants are read from one native table
(`kwxConstants_IntCount` / `kwxConstants_IntTable`, generated by kwxgen) rather
than one FFI call per constant, so importing `kwx` creates about 90 thunks —
the pointer-valued constants (colours, brushes, fonts, art IDs) plus the two
table accessors — instead of the previous ~1,580.

### Transpile cache

TypeScript transpiles are cached on disk so a repeat run of an unchanged module
skips both the transpile and the Sucrase load. A cache hit is reported with the
`transpile-cache-hit` mark and a miss with `transpile-cache-miss`; a hit never
touches Sucrase at all.

- The cache is **enabled by default**.
- Set `KWX_TS_NO_CACHE` to any non-empty value to disable it; the runtime then
  behaves exactly as before (no cache reads or writes).
- The cache directory is `KWX_TS_CACHE_DIR` when set; otherwise
  `%LOCALAPPDATA%\kwx_ts\transpile` on Windows, `$XDG_CACHE_HOME/kwx_ts/transpile`
  when `XDG_CACHE_HOME` is set, else `$HOME/.cache/kwx_ts/transpile`.
- A source edit always produces a cache miss. The key also includes the embedded
  Sucrase bytecode size, so rebuilding the bundle invalidates every entry.
- Sources larger than 8 MiB are never cached.

The Sucrase bundle and the embedded `kwx` corpus are precompiled to QuickJS
bytecode at build time (see `CMakeLists.txt`), so an
`<embedded:…>` module skips `transpile-*`, `module-compiled` and
`module-factory-built`; `embedded-bytecode-loaded` marks the
`JS_ReadObject` + `JS_EvalFunction` step instead.

## Platform surface (`kwx/platform`)

Generated bindings import their FFI primitives from the bare specifier
`"kwx/platform"`, which the runtime resolves to an embedded module. The module
is implemented over `globalThis.kwxHost`; importing it under any other runtime
throws a clear "requires the kwx_ts runtime" error.

| Export | Notes |
|--------|-------|
| `platform` | Platform name (`"windows"`, `"darwin"`, `"linux"`). |
| `args` | Command-line arguments after the entry file. |
| `exit(code?)` | Terminates the process (sentinel-based unwind). |
| `dlopen(name, symbols)` | Returns a lazy symbol table backed by the statically linked kwxFFI surface. Individual thunks are created on first property read; the library is **never** opened — the `name` argument is informational only. |
| `pointerOf(value)` | Wraps a buffer/value as an opaque pointer. |
| `readCString(ptr)` | Reads a NUL-terminated C string. |
| `arrayBufferView(ptr, byteLength)` | Non-owning `ArrayBuffer` view over `byteLength` bytes at `ptr`. |
| `Callback(definition, fn)` | Registers a native callback; supports `.pointer` and `.close()`. |
| `Pointer` | TypeScript type for an opaque native pointer (`bigint | null`). |

Additionally available globally: `console` and `TextEncoder`.

Not available: file and environment APIs, timers (`setTimeout` /
`setInterval`), `queueMicrotask`, `fetch`, and every other Web/Node/Deno API.

## Module resolution

`kwx_ts` uses a CommonJS-style loader with a Sucrase transpile step:

- Specifiers are **relative or absolute filesystem paths**. There is no npm
  resolution and no remote URL support.
- Candidates are tried in order: the exact path, then `.ts`, `.tsx`, `.js`,
  `.mjs`, `.cjs` appended to the path, then `<path>/index.<ext>` with the same
  extension list.
- `.js` / `.cjs` files that contain no `import` / `export` tokens are loaded
  directly (fast path). Everything else — including every `.ts` file — is
  transpiled with the embedded Sucrase bundle using the `typescript` and
  `imports` transforms.
- The bare specifiers `"kwx"`, `"kwxTypeScript"`, and `"@kwx"` resolve to the
  **embedded binding bundle** rather than a file on disk.
- The bare specifier `"kwx/platform"` resolves to the embedded platform module.

### The `"kwx"` virtual module

Importing `"kwx"` gives you the entire kwxFFI binding corpus (all generated
`wx*` wrappers, constants, helpers, and the app functions) plus the raw `lib`
object:

```ts
import {
    BOTH,
    createWxString,
    DEFAULT_FRAME_STYLE,
    EVT_CLOSE_WINDOW,
    exitMainLoop,
    ID_ANY,
    initialize,
    run,
    setTopWindow,
    shutdown,
    wxClosure,
    wxFrame,
} from "kwx";
```

This bundle is **embedded inside the executable** as a compiled CommonJS asset.
No `wx/` sources and no `dist/` bundle are read from disk at runtime.

See `examples/hello.ts` for a complete, minimal program.

## Event-loop model

wxWidgets owns the main event loop:

- `run()` calls into the native main loop and **blocks** until the loop ends.
- `exitMainLoop()` requests the loop to stop (it must **not** be used to close
  a frame from inside a close handler — just call `exitMainLoop()`).
- Pending QuickJS micro-task jobs are drained from wxWidgets dispatch hooks, so
  promise callbacks and jobs scheduled by JavaScript still run while the GUI is
  alive.
- JavaScript callbacks (registered via `Callback` from `kwx/platform`)
  execute **synchronously on the GUI thread**.

A typical program creates widgets, wires `wxClosure`-backed event handlers,
calls `frame.Show()` / `setTopWindow(frame.ptr)`, then calls `run()` and shuts
down with `shutdown()`.

> Keep every `Callback` and `wxClosure` object referenced until after
> `run()` returns. If one is garbage-collected the native function pointer
> becomes dangling and the process can crash. Close them (`.close()`) after the
> loop exits.

## Limitations

- **No permissions model.** The program simply has whatever access the bindings
  give it.
- **No network access** and **no npm / remote module resolution**.
- **Callbacks**: a fixed pool of **64** callback slots, each limited to the
  three-pointer `void` signature
  (`parameters: ["pointer", "pointer", "pointer"], result: "void"`).
- **No workers** and no multi-threading from JavaScript.
- **No ESM live bindings and no top-level `await`.** Modules are CommonJS;
  imports are snapshots.
- **Platforms**: Windows x64, macOS Universal, and Linux native. Windows ARM64
  is not supported.

## Building

The executable is built with CMake from the **repository root** (the single
root `CMakeLists.txt` builds kwx_ts, the binding generator, and the fetched
dependencies in one `build/` tree). QuickJS-ng and kwxFFI/wxWidgets are fetched
automatically via `FetchContent` on the first configure (network access
required once).

### Windows x64

Requires MSVC (or clang-cl) and Ninja.

```
cmake --preset ninja-multi
cmake --build build --config Debug --target kwx_ts
```

The executable is produced at `bin\Debug\kwx_ts.exe`.

### macOS Universal (`x86_64` + `arm64`)

Requires the Xcode command-line tools.

```
cmake --preset macos-universal
cmake --build build-macos --config Debug --target kwx_ts
lipo -info bin/Debug/kwx_ts
```

`lipo -info` should report the binary as containing both `x86_64` and `arm64`
slices (a Universal binary). The `.app` bundle fallback is **not** enabled, so
the output is a plain executable, not a `.app`.

### Linux native

Requires `pkg-config` and the development packages for `gtk+-3.0` and `x11`,
plus Ninja or Make.

```
cmake -B build -S . -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build --config Debug --target kwx_ts
```

### Release size and startup

Every dependency (wxWidgets, kwxFFI, QuickJS-ng) is compiled with function and
data sections and linked with section garbage collection (`-ffunction-sections
-fdata-sections` + `-Wl,--gc-sections`; `/Gy /Gw` + `/OPT:REF /OPT:ICF` on
MSVC). Release additionally strips the debug sections contributed by the static
libraries. On Windows this takes the executable from roughly 22 MB to 19 MB and
removes most of the page-fault work the loader does before `main()` runs.

### Self-contained output

The produced executable is self-contained: it does not load kwxFFI, QuickJS, or
wxWidgets shared libraries. Apart from OS-provided libraries (Windows system
DLLs, macOS frameworks, Linux GTK3/X11 plus libc) nothing is loaded at runtime.

Windows ARM64 is unsupported.

## Maintainer note: regenerating the runtime bundle

`runtime/kwx_runtime.js` is a snapshot of the generated `wx/` corpus (it is the
embedded `"kwx"` virtual module) and `runtime/kwx_platform.js` is the snapshot
of `src/kwx_platform.ts`. **Regenerate both whenever `wx/` or
`src/kwx_platform.ts` changes** so the embedded assets stay in sync:

```
cd tools
npm install
node build_runtime_bundle.cjs
```

The regenerated assets are committed. Users of `kwx_ts` never
need Node or npm. The build compiles it to QuickJS bytecode with `qjsc`, so no
separate step is required after regeneration. See `third_party/README.md` for
the full set of one-time maintainer scripts.
